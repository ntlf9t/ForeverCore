# Trixx34/Trinity-Forever-Modules 1c593e7567: bigger navmesh A* node pool

Trixx34, from LatvjuAvs/TrinityCore 89ff5fcf3a (GPL-2.0). Reviewed 2026-11-16 against `everlake` 0d9a4b9145.

**Claim.** Long routes ran out of A* nodes (`DT_OUT_OF_NODES`) and came back partial. Their example: Kharanos to Thelsamar,
about 2,400 yd. They raised `dtNavMeshQuery::init` from 1024 to 32768 nodes for every query.

**Check.** We were at 8192 already (raised from 1024 for the same reason when the bots came in). Bots get a 512-poly cap
(`MAX_PATH_LENGTH`), but the cap only limits the path that comes back. The node pool limits how far A* searches, and a
search that runs out returns a path to the node closest to the target. That node can be a dead end. A search that only hits
the poly cap is different: it returns a prefix of the real route, so the bot still makes progress. Nothing counted either
case, so the live logs could not show it.

Measured offline on our Forever navmesh (maps 0 and 1). A standalone Detour probe uses the same filter as a bot's
`PathGenerator`: `dtQueryFilterTC` slope cost with `Pathfinding.SlopeCoefficient = 1.0`, road cost 1.0
(`Pathfinding.PreferRoads = 0`) and a 512-poly cap. It ran 60 random connected routes per distance band per map, and
counts the searches that came back with `DT_OUT_OF_NODES`:

| Straight distance | 1024 nodes | 8192 (ours) | 32768 | 65535 |
|---|---|---|---|---|
| 100-300 yd | 3-7% | 0% | 0% | 0% |
| 300-600 yd | 15-17% | 2-3% | 0-2% | 0% |
| 600-1000 yd | 47-65% | 8-12% | 2-3% | 0% |
| 1000-1600 yd | 68% | 12-15% | 2-3% | 0% |
| 1600-2400 yd | 100% | 33-37% | 7-8% | 0% |
| 2400-3500 yd | 98-100% | 72-78% | 18-25% | 0% |

These are exactly the distances bots ask for. `UnifiedTravelGraph` walk legs go up to 600 yd (`kMaxWalkEdgeYds`), the first
and last attach legs up to 1,500 yd (`kFarAttachYds`), and many callers path straight to a quest or grind target. The
Kharanos to Thelsamar route (2,487 yd straight) needs 44,247 nodes on our mesh. It ends 1,355 yd short at 8192 and 308 yd
short at 32768. Only 65535 completes it.

Detour indexes nodes with 16 bits, so 65535 is the largest pool `dtNavMeshQuery::init` accepts.

**Cost.** Memory per query object (Detour allocations counted during `init`): 1024 = 0.04 MB, 8192 = 0.33 MB,
32768 = 1.33 MB, 65535 = 2.66 MB. `MMapManager` holds one query per loaded map instance: one per continent plus one per
dungeon, raid or battleground copy. This change raises only the open-world queries (instanceId 0). Instances keep 8192, so
memory grows by about 1 MB per continent (2.3 MB at 65535), not per dungeon copy.

Time: a search only uses extra nodes when it would otherwise have run out. Average time per search barely moved
(600-1600 yd: about 1 ms at 8192, 1-1.6 ms at 32768, on an i7-9750H). The worst single search at 300-1600 yd went from about 3-5 ms
to 11-17 ms at 32768 (20 ms beyond 2,400 yd), and to 35 ms at 65535. A search runs inside the map update under the per-map `NavExecLock`. At
8192 a failed search also costs about 3 ms, and the bot then searches again from wherever it stopped.

**What changed.**
- `Pathfinding.NavMeshQueryNodes` (worldserver.conf, default 32768, clamped 8192-65535, read at startup) sets the
  open-world pool. Instanced maps stay at 8192 (`MMapManager::INSTANCE_QUERY_NODES`).
- `PathGenerator` keeps the `findPath` status. `dtQueryFilterTC::TallyPath` counts `out_of_nodes` (`DT_OUT_OF_NODES`) and
  `poly_cap` (`DT_BUFFER_TOO_SMALL`), globally and per map. `.playerbot roadstats [list|<mapId>]` shows them, so live bots
  can confirm the offline numbers and show whether 65535 is worth trying.
- Startup logs the pool sizes ("Navmesh A* node pool: ...").

32768 is the default, not 65535. At 300-1600 yd it removes about 75% of the out-of-node searches (31 of 360 routes at
8192, 7 at 32768) and keeps the worst search under about 20 ms. The counter shows what is left. If `out_of_nodes` stays high, set the option to 65535: no
rebuild needed.

**Caveats.** The probe picks only routes that a 65535-node search completes, so the 65535 column is 0% by
construction. Routes that need even more nodes exist but are not in the table. The navmesh measured is the 2026-11-06 extraction (mmap version 16). The live PTR mmaps are regenerated by
our generator and may differ in detail. Non-bot creatures share the same query, so a creature asked for a very long path
can also search further now. Creature paths are short in practice.

**Test.** `tests/game/NavMeshQueryNodes.cpp`:
- loads a header-only `0000.mmap` from a temp dir and checks the pool of the world query (32768, then 65535 when
  configured) and of an instance query (8192);
- checks the clamp at both ends;
- checks the two new counters, globally and per map.

Run against the real `MMapManager`, `dtQueryFilterTC` and Detour sources: 27 checks pass. With the pool hard-coded back to
8192, 2 checks fail.

PTR: `.playerbot roadstats list` after an hour with bots out. `out_of_nodes` should be well under 1% of `paths_run` on
maps 0 and 1.

**Verdict:** take, adapted. The bigger pool goes on open-world maps only, it is a config option, and it comes with the
counter.
